1 Resumen ejecutivo

El backend está en un estado de refactor a medio terminar con deuda de seguridad grave. Hoy hay 33 endpoints de dominio cableados (más /health) en 8 routers, pero existe en paralelo un árbol hexagonal completo en app/modules/* que nadie cablea (código muerto) y que duplica auth/articles/ai. La superficie viva contiene fallos de control de acceso explotables, viola la máquina de estados declarada y arrastra 3 contratos rotos con el frontend. Este resumen propone una superficie de 60+ endpoints en 15 dominios marcando lo que existe, lo parcial y lo que falta, con prioridades para cerrar primero la seguridad y alinear el flujo editorial.

2 Hallazgos de seguridad (P0)

🔴 Router IA 100% público — /api/v1/ai/models · /assist · /ingest · /format

Ningún Depends: abuso ilimitado del LLM y envenenamiento del RAG (Qdrant) por cualquier anónimo, para cualquier article_id.

🔴 GET /api/v1/articles/{id} sin auth ni ownership

Cualquier anónimo lee borradores / in_review / rejected ajenos conociendo el UUID.

🔴 PUT /api/v1/agents/claude-defs/{name} — path traversal + tampering de prompts

name sin sanear se interpola en la ruta del fichero; permite escribir fuera del directorio y reescribir los prompts del pipeline. Sin gate de admin.

🔴 GET/PUT /api/v1/config sin gate de admin

Cualquier usuario logueado lee la config global (incluido SECRET_KEY) y la sobreescribe con un dict arbitrario replicado a varias rutas.

🔴 approve / reject / assign-reviewer sin rol ni ownership

Solo exigen estar logueado: cualquier autor publica o rechaza artículos de otros. El RBAC (author/reviewer/admin) es puramente declarativo.

🟠 CORS y secretos

allow_origins=['*'] junto a allow_credentials=True (combinación inválida por spec) y SECRET_KEY con default hardcodeado.

3 Máquina de estados: declarado vs. real

✅ Declarado (state-machine.md · DESIGN §2.3)

draft ──submit──▶ in_review ──approve──▶ approved ──publish──▶ published ▲ │ └──── reject ──────┘ (vuelve a draft) publish = automático tras approve humano (ADR-004)

❌ Real (código actual)

draft ──submit──▶ in_review ──approve──▶ PUBLISHED │ (¡salta 'approved'!) └──reject──▶ rejected ✗ sin salida approved: NUNCA usado publish : SIN endpoint — lo hace el agente publicador escribiendo la BD (viola ADR-004)

Consecuencia: el estado approved nunca se materializa, un artículo rejected queda en callejón sin salida, y la publicación ocurre sin el gate humano que exige el ADR-004.

7 Roadmap por fases

P0  Seguridad & RBAC base

  • Cerrar auth en todo /ai/* + rate-limit.
  • Ownership en GET /articles/{id}.
  • Sanear name + gate admin en claude-defs.
  • Admin + schema + redacción de secretos en /config.
  • Gate de rol en approve/reject/assign/publish.
  • Endurecer CORS y SECRET_KEY.
  • PUT /users/{id}/role · GET /users/reviewers; helpers require_role.

P1  Coherencia funcional

  • Alinear máquina de estados: approve→approved, POST /publish, resubmit.
  • El agente publicador deja de publicar directo (ADR-004).
  • GET /reviews/queue (cola del revisor).
  • POST /auth/refresh + emitir refresh_token.
  • reject lee comment del body; read-all + unread-count.
  • GET /agents/{id}/runs/{run_id}.
  • Feed público: /feed + /articles/{id}/view.

P2  Completitud & observabilidad

  • CRUD de usuarios; DELETE /articles/{id}.
  • Subida de portada (cover_url → MinIO).
  • /dashboard/stats y /metrics/agents (poblar tokens_used).
  • Paginación SQL real; response_model en todos.
  • SSE sobre Redis (multi-worker); búsqueda con q.

🧭 Recomendación de arquitectura

  • Unificar routers vs. módulos hexagonales: una sola implementación.
  • Introducir capa de casos de uso (regla fastapi-style.md).
  • Centralizar las transiciones de estado en el dominio.
  • Unificar config: vector_size 1536 (yaml) vs. 64 (fallback).
